## 0. Gateway backlog

`ThreadingHTTPServer` listens with a backlog of 5 (`request_queue_size`).
Raise it to 128 in `gateway.make_server`, with a test that reads the value.
It's cheap, and it removes one candidate from readiness item 8 (connections
dropped at concurrency 16).

## 1. Container backends

**Config.** The runtime is chosen per backend and stored in `config.json`:

```
llmctl config runtime vllm docker --image vllm/vllm-openai@sha256:<digest>
llmctl config runtime vllm host          # default; today's behaviour
llmctl run <model> --runtime docker      # per-launch override
```

- The image must be pinned by digest (`…@sha256:`). A tag is refused unless
  `--allow-tag` is given (for development). llmctl never pulls; a missing
  image is an error that names `docker pull` / `docker load`.
- Host processes stay the default. Development is unchanged.

**How it runs.** `process.start` launches `docker run --rm --name
llmctl-<name>` **attached** (no `-d`) as the tracked child. Then the PID,
the log file, `stop`, `restore`, `--wait` and zombie detection all keep
working unchanged. `stop` sends SIGTERM, which docker forwards to the
container (`--sig-proxy` is the default when attached). It then runs
`docker rm -f llmctl-<name>` as a fallback, and `reconcile` does the same
for leftovers after a crash.

**The `docker run` line** (vLLM):

- GPU: `--device nvidia.com/gpu=<i>` (CDI) when the host has CDI specs,
  otherwise `--gpus device=<i>`. Default GPU 0, set with `--gpu N`. This also
  starts the "GPU placement" should-have item.
- Models: `-v $MODELS_DIR/<model>:/models/<model>:ro`, and the argv points at
  `/models/<model>`. Only the one model is mounted, not the whole directory.
- Port: `-p <bind_host>:<port>:<port>`, so `config bind 127.0.0.1` keeps
  applying. The engine listens on `0.0.0.0` inside the container.
- Env: the same offline and telemetry variables as host launches
  (`HF_HUB_OFFLINE`, `VLLM_NO_USAGE_STATS`, …), plus any `-E` values.
- `--ipc host` or `--shm-size`, which vLLM needs for its workers.
- No host toolchain variables: the image brings its own compiler.

**Network: needs a decision.** Docker has no mode for "no network except
the published port". `--network none` disables publishing, and `--internal`
networks can't publish either. There are three options:

- **A (proposed for M0.3):** default bridge plus the published port.
  Egress is blocked by the host's `DOCKER-USER` iptables rule, which the
  admin guide documents and `llmctl doctor` can check. It's simple and works
  with today's gateway. M0.5's "zero egress" test verifies it.
- **B:** `--network none`, with the engine on a unix socket (`vllm --uds`)
  in a bind-mounted directory. The gateway and the health probes then speak
  HTTP over UDS. This is the strongest isolation, but it's about two extra
  days and llama-server's UDS support needs checking.
- **C:** an `--internal` network, with the gateway itself in a container
  attached to it. That's the Compose model, and it belongs with readiness
  item 6.

**Reporting.** The launch records `image` (the ref as given) and
`image_digest` (from `docker image inspect`, the repo digest). They then
appear in:

- `ps`: a column, shortened to `vllm-openai@sha256:1a2b3c4d`;
- `/v1/models`: under the `llmctl` object, as `runtime`, `image` and
  `image_digest`;
- the log: the first line of the model's log file, and the gateway's
  startup line for that model;
- the cluster heartbeat, so `ps --all` shows other nodes' digests.

**llama.cpp** follows the same launcher, with `ghcr.io/ggml-org/llama.cpp`
`server-cuda` pinned by digest. orin needs a Jetson (L4T) image, which isn't
in M0.3.

**Tests:** argv building for each option (CDI or `--gpus`, bind host, `:ro`,
env), refusing a tag, and `ps`/`describe` fields, all with a faked
`docker`. One live test on ws starts Qwen3-0.6B in `vllm/vllm-openai`
through the gateway, after a heads-up to A0.

## 2. Per-model compile cache

vLLM keeps `torch.compile`, Triton and FlashInfer artifacts under
`VLLM_CACHE_ROOT` (default `~/.cache/vllm`) and `~/.cache`. The cache key
includes the vLLM version, the model config, the compile config and the GPU
architecture. A shipped cache is therefore only valid for the same image
digest and GPU arch. The 4090 and the L40S are both sm_89, so a cache
built on ws is valid on PS6 for the same image.

- Shipped cache: an optional `cache/vllm/` subtree in the bundle, listed in
  the manifest with the engine it was built with (see the format below).
  `install` places it at `MODELS_DIR/<model>/.llmctl-cache/vllm/`
  (read-only, like the weights).
- Writable copy: `STATE_DIR/cache/<model>/<image-digest>/`. On first start
  it's seeded from the shipped cache, and it's reused on later starts. It's
  mounted at `/cache` with `VLLM_CACHE_ROOT=/cache/vllm` and
  `XDG_CACHE_HOME=/cache`.
- Match rules. Every start logs the rule that matched:
  - `digest`: container runtime, where the `image` digest and `gpu_arch`
    equal the launch's. This is the only rule a container launch accepts.
  - `engine_version`: host runtime only, where `engine_version` and
    `gpu_arch` match. It doesn't pin torch or CUDA, so it's logged as
    `cache rule: engine_version (dev fallback)`.
  - `none`: nothing matched. The log says
    `cold start: shipped cache built for <x>` and the start compiles.
- Host runtime: the same `VLLM_CACHE_ROOT` per model, so development gets
  per-model caches too.
- `llmctl cache export <model> <dir> [--json]`: writes the warm cache of a
  running or stopped model as a manifest-ready subtree. Its `caches` entry
  records the digest and arch it was built with. That's how A0 builds the
  shipped cache on ws.

Verifying it: start cold, export, wipe, install, then start again. The
second start must log a cache hit (`Directly load the compiled graph`), and
its KV cache size must match a warm start.

## 3. Fixed KV size per model

The vLLM flag is `--kv-cache-memory-bytes` (there is no
`--kv-cache-memory`). It already works per model today:

```
llmctl run qwen3.5-9b -X '--kv-cache-memory-bytes=6G'
```

`-X` is stored in the autostart manifest, so `restore` and `restart`
keep it. The plan adds:

- a `--kv-cache-mem` option on `run`, mapped for vLLM, so it shows in the
  menu and `ps`;
- a warning when a hybrid model (`hf_is_hybrid`) starts on vLLM without a
  fixed KV size;
- a README note on why (a warm restart can OOM in `chunk_gated_delta_rule`).

The KV size also goes in a serving file (section 6), which is how a bundle
ships it.

## 4. `llmctl install`

```
llmctl install <bundle-dir>            # verify, then place into MODELS_DIR
llmctl install oci://<registry>/<repo>@sha256:<digest>   # oras pull, then the same
llmctl install <bundle-dir> --name <folder> --replace
```

The manifest format is defined below. Behaviour:

1. Read `llmctl-manifest.json` from the bundle root. Reject an unknown
   `schema`, and reject paths that are absolute, contain `..`, or are
   symlinks.
2. Copy **only the listed files** into
   `MODELS_DIR/.install-<name>.<pid>/`, hashing while copying. Unlisted
   files are ignored, so a signature file next to the manifest does no
   harm. If any size or sha256 doesn't match, the install is refused: the
   temp dir is deleted, and the error lists every mismatching path.
3. If all files match, rename the temp dir to `MODELS_DIR/<name>`. An
   install never touches an existing folder: if `name` exists, it's refused
   (name conflict). Versions sit side by side as `--name <model>-<version>`,
   so a rollback only switches what's served (section 6). `--replace`
   overwrites explicitly. It's refused while that folder is being served,
   and the old copy is only removed after the new one is in place.
4. Write `.llmctl-source.json` with `source: "install"`, `repo_id`,
   `revision`, `license`, `format`, `files`, the per-file sha256, and the
   sha256 of the manifest itself. `list` gains revision and licence columns,
   and `llmctl verify <model>` re-hashes against the sidecar.
5. `download` and `update` keep working as they do. `update` refuses an
   installed model; there is nothing to re-check against.

**For scripts.** `install --json` and `cache export --json` print one JSON
object on stdout, and human messages go to stderr:

```json
{"ok": true, "name": "qwen3.5-9b-2026.10.1", "path": "/models/qwen3.5-9b-2026.10.1",
 "manifest_sha256": "…", "files_verified": 14, "bytes": 19328430112,
 "cache": {"kind": "vllm", "seeded": false, "rule": "none"}}
```

On failure the object has `"ok": false`, an `error` code, a `message`, and
for mismatches a `mismatches` list (`path`, `expected`, `actual`, or
`missing`). Exit codes are fixed and documented:

| Code | Meaning |
|---|---|
| 0 | installed or exported |
| 2 | usage error (click's own) |
| 3 | bad manifest: unreadable, unknown schema, unsafe path, missing required key |
| 4 | checksum or size mismatch, or a listed file missing |
| 5 | name conflict: the target exists, or `--replace` was given while it's served |
| 6 | source unreachable: `oras` missing or the pull failed |
| 1 | anything else |

`oci://` shells out to the `oras` CLI (it must be on the host), pulling into
a temp directory. Its files are expected to be the bundle directory as
pushed with `oras push <ref> <files…>`.

### Manifest format (`llmctl-manifest.json`, schema 1)

```json
{
  "schema": "llmctl-manifest/1",
  "name": "qwen3.5-9b",
  "model": {
    "id": "Qwen/Qwen3.5-9B",
    "revision": "4f1c…e2",
    "format": "hf",
    "license": "apache-2.0",
    "license_file": "LICENSE"
  },
  "files": [
    {"path": "config.json", "size": 1534, "sha256": "9b1e…"},
    {"path": "model-00001-of-00004.safetensors", "size": 4967215360, "sha256": "…"},
    {"path": "cache/vllm/torch_compile_cache/…", "size": 81234, "sha256": "…"}
  ],
  "caches": [
    {"kind": "vllm", "path": "cache/vllm",
     "engine": "vllm", "engine_version": "0.29.0",
     "image": "vllm/vllm-openai@sha256:…", "gpu_arch": "sm_89"}
  ]
}
```

- `schema` is required and versioned. Unknown top-level keys are ignored,
  so a bundle builder can add its own (a bundle id, a build time).
- `name` is the folder under `MODELS_DIR`, and `--name` overrides it.
- `model.id` and `model.revision` are the upstream repo and commit. They're
  free text, so non-HF sources fit too. `format` is `hf` or `gguf`.
  `license` is an SPDX id or `other`, and `license_file` must be one of
  `files` when given.
- `files` lists every file to install. `path` is relative and POSIX; `size`
  is in bytes; `sha256` is lowercase hex.
- `caches` is optional. Each entry names a subtree of `files` and what it
  was built with. llmctl only seeds a cache whose `image` (container
  runtime) or `engine_version` (host runtime) and `gpu_arch` match the
  launch.
- llmctl doesn't verify signatures. A signer signs the manifest bytes, and
  the per-file hashes extend that to every file.

`llmctl manifest <model-dir>` writes this file for an existing folder, so a
bundle can be made from a downloaded model without extra tooling.

## 6. Serving files: `llmctl apply`

The question was whether a bundle can carry a serving profile that's applied
offline from a file. Today it can't. `run` options are given on the command
line, through the menu, or as user profiles in `profiles.json`, and none of
them is a file you hand over. The plan adds the model part of readiness
item 6 now. It reads only local files and never touches the network.

```toml
# serve.toml: a fragment, one model; a host file is several of these
[models.qwen35-9b]
model   = "qwen3.5-9b-2026.10.1"      # folder under MODELS_DIR
group   = "qwen3.5-9b"                # stable route name across versions
backend = "vllm"
runtime = "docker"                    # image from config or `image = "…@sha256:…"`
port    = 8101
gpu     = 0
ctx     = 32768
n_parallel = 8
args    = ["--kv-cache-memory-bytes=6G", "--quantization=fp8"]
env     = { VLLM_LOGGING_LEVEL = "INFO" }
```

```
llmctl apply serve.toml [more.toml …] [--dry-run] [--prune] [--json]
```

- **Idempotent.** For each entry, apply builds the launch exactly as `run`
  would and compares it with what's recorded. An identical running entry is
  left alone, a changed one is restarted, and a missing one is started.
  `--dry-run` prints the diff. `--prune` also stops models that aren't in
  any of the given files; without it, apply never stops anything else.
- **Fragments merge.** A bundle ships its own fragment, and the host file
  is several fragments together. A table key defined twice is an error that
  names both files.
- **Rollback in under 5 minutes.** Two installed versions differ only in
  `model` (and maybe the cache). Switching back is: edit or replace the
  fragment, then `apply`. The `group` keeps the route name, so clients
  don't change. With the old version's compile cache already seeded, the
  restart is warm.
- **Validation.** It covers unknown keys, a model folder that doesn't
  exist, a tag instead of a digest, and a port in use. Errors name the file
  and the key, and TOML syntax errors give the line.
- **Format.** TOML, read with Python's stdlib `tomllib` (3.11+), so there's
  no new dependency. The readiness doc said YAML; that needs PyYAML. This is
  a decision for Alex.
- Autostart then follows the applied state, as it does for `run`.
  Making the files themselves the boot source (a systemd unit that runs
  `apply`) is the rest of readiness item 6, and comes after.
