# Plan: metrics, failure behaviour, structured logs and traces

Requested by SS6M A0 on 2026-10-23 for M0.4 (observability and operations).
It covers items 7 and 8 and the "Structured logs" should-have of
`docs/ss6m-production-readiness.md`. Status: **approved by Alex on 2026-10-23** (all six decisions as recommended, with the scrape-only metrics token).
Everything here is general llmctl behaviour; nothing names PS6 or SS6M.

A0's stack, for context: VictoriaMetrics (Prometheus scrape format) running on
lab scrapes ws and orin over the LAN; Vector → VictoriaLogs; an OpenTelemetry
collector with Jaeger v2; Perses dashboards.

## What exists today (checked in the code)

- The gateway (stdlib `ThreadingHTTPServer`) proxies every call. It already
  forwards `traceparent`, `tracestate` and `X-Request-Id` untouched, because
  only hop-by-hop headers are dropped. It has `/healthz` and `/readyz`, and it
  writes plain-text lines to its log file (access lines, failover, spill).
- **No supervisor.** A model that crashes stays down until `restore` or a
  manual `run`. Worse, the gateway drops a dead PID from its model list, so a
  client then gets **404 `model_not_found`**, not 503.
- A backend that dies mid-stream: the relay logs "upstream broke" and closes
  the connection. The client sees a truncated stream with no error.
- llama-server isn't started with `--metrics`; vLLM and SGLang expose
  `/metrics` on the model's port, which is bound to `config bind` (often
  127.0.0.1) and changes between runs.
- vLLM v0.29 doesn't log prompts by default: no "Received request" lines in
  today's logs. llama-server logs prompts only with `--verbose`; SGLang only
  with `--log-requests`. llmctl passes none of these. The pinned vLLM image
  ships the OpenTelemetry SDK and OTLP exporter, so `--otlp-traces-endpoint`
  works when passed through `args:`.

## Design

### 1. Gateway `/metrics` (Prometheus text, no new dependency)

In-process counters and histograms, thread-safe, rendered on scrape. Labels:
`model`, `node`, `backend`, plus `code` where it applies. Cardinality is
bounded by the running models.

| Metric | Type | Notes |
|---|---|---|
| `llmctl_requests_total{model,node,backend,status}` | counter | `status` = HTTP status of the reply to the client |
| `llmctl_request_errors_total{model,node,backend,code}` | counter | the gateway's own error codes (`upstream_unavailable`, `model_unavailable`, `busy`, …) and `stream_aborted` |
| `llmctl_request_duration_seconds{model,node,backend}` | histogram | request start to last byte |
| `llmctl_time_to_first_token_seconds{model,node,backend}` | histogram | streamed calls only: request start to the first SSE event that carries content. Buckets 0.05, 0.1, 0.2, 0.3, 0.5, 0.75, 1, 1.5, 2, 3, 5, 7.5, 10, 15, 20, 30, 60 s. |
| `llmctl_tokens_total{model,node,backend,direction="in"\|"out"}` | counter | from `usage` in the reply: always for non-streamed calls, and for streamed calls when the client asked `stream_options.include_usage`. The engines' own token counters come through section 2. |
| `llmctl_requests_in_flight{model,node,backend}` | gauge | calls the gateway is relaying |
| `llmctl_requests_queued{model,node,backend}` | gauge | read at scrape time from the engine (vLLM/SGLang waiting count, llama `/slots`) |
| `llmctl_spills_total{model,from_node,to_node}`, `llmctl_failovers_total{model,from_node,reason}` | counter | |
| `llmctl_node_up{node}` | gauge | from the cluster table (1/0) |
| `llmctl_instance_state{model,node,state}` | gauge | 1 for the current state: `starting`, `ready`, `restarting`, `crashed`, `stopped` |
| `llmctl_instance_restarts_total{model,node}` | counter | supervisor restarts |
| `llmctl_build_info{version,node}` | gauge | |

`/metrics` follows the API-key policy like `/v1/*`: open when auth is off,
and a scraper sends `Authorization: Bearer <key>` when it's on (vmagent
supports this).

### 2. Backend metrics for a remote scraper

- `GET /metrics/backends/<model>` re-exports that local instance's `/metrics`
  with `model`, `node` and `backend` labels added to every sample.
- `GET /metrics/sd` returns Prometheus **HTTP service discovery** JSON
  (`http_sd_configs`, which vmagent supports). It lists one target per running
  local instance, with path and labels, so the scrape config stays fixed when
  ports change.
- llama-server gets `--metrics` on every launch.
- The README documents a vmagent scrape config for both.

### 3. Failure behaviour (item 8)

**Supervisor in the gateway.** It's always running, already owns the
autostart list, and `restore` logic exists.
- Every few seconds it looks for autostart models whose process died without
  `llmctl stop`. It restarts them from their launch spec, the same path as
  `restore`, with exponential backoff: 2, 4, 8 … s, capped at 60 s, and reset
  after 10 min ready.
- After `max_restarts` within 10 min it gives up: state `crashed`.
- Policy per instance: `run --restart on-failure|never`,
  `--restart-max N`, and the same `restart:` keys in serving files (additive).
- `llmctl stop` still means stopped: it removes the model from autostart, so
  it's never restarted.
- This also closes the old card about `stop` and crashed models.

**What clients see:**
- **A configured model that's down or restarting:** 503
  `model_unavailable`, with `Retry-After` and the OpenAI-style JSON error
  body. Today that case returns 404 `model_not_found`, which is wrong for a
  model that is configured (decision 4).
- **A model that dies during a call that hasn't replied yet:** the
  connection is refused or reset at once, so the client gets 503
  `model_unavailable` within about a second. A failover candidate is tried
  first, as today.
- **A model that dies mid-stream:** the gateway sends a final SSE event
  `data: {"error": {"code": "model_unavailable", "type": "server_error",
  "message": …}}` and ends the chunked stream cleanly instead of cutting it.
  A non-streamed reply that breaks mid-body can't change its status. The
  connection is closed, and the error is logged and counted.
- **Optional hang guard:** `gateway.first_token_timeout`, off by default. It
  answers 504 if nothing arrives within N s. A killed backend doesn't need
  it, but a stuck one (SIGSTOP, GPU hang) does.

**Seeing state during recovery:**
- `llmctl ps` gets STATE and RESTARTS columns, and `llmctl ps --json`.
- `/v1/models` `status` gains `restarting` and `crashed` (new values),
  plus `restarts`.
- `llmctl events`, a `-f` tail of the supervisor's state changes.

Target, tested: a SIGKILL of the engine gives an explicit 503 within 10 s,
including on an open stream, and the model is serving again within 120 s.
The 120 s holds for warm-cache starts: Qwen3.5-4B and Ministral measured
under 60 s today. `scripts/chaos-test.sh` runs the kill, timing and recovery
against a running model, for A0's chaos test and for release checks.

### 4. Structured logs

- `llmctl config gateway-log json|text`. Default `text`: logs aren't in
  the 1.x contract, and the human format stays the default.
- JSON lines go to the gateway log file and stdout, so `journalctl` and Vector
  read them.
- One access line per call with:
  - when and where: `ts`, `level`, `node`;
  - ids: `request_id`, `trace_id`;
  - the call: `method`, `path`, `model`, `backend`;
  - the result: `status`, `code`, `duration_ms`, `ttft_ms`, `tokens_in`,
    `tokens_out`, `bytes_out`, `failovers`;
  - `client`.
- Supervisor, failover and spill events go out as JSON lines too.
- **Request id:** take `X-Request-Id` from the client (validated: at most 128
  printable characters), else generate one. Forward it to the backend
  (vLLM uses it as its request id), and return it on every reply, errors
  included.
- **No prompt or completion text in any mode.** I'd not build a content-
  logging debug mode at all, so there's no switch to leave on by mistake.
  The engines' own prompt logging stays off; it's checked above and pinned
  by a test that the generated commands never contain
  `--enable-log-requests`, `--log-requests` or `--verbose`.

### 5. Trace propagation

- `traceparent`/`tracestate` already reach the backend. The gateway will
  continue the trace: it creates its own span and sends the backend a
  `traceparent` naming that span as parent, starting a new trace if the
  client sent none.
- **OTLP export, off by default** (no egress):
  `llmctl config gateway-otlp http://collector:4318`.
  - A minimal OTLP/HTTP JSON exporter, stdlib only, batched on a background
    thread, dropping spans rather than blocking.
  - One server span per call, with a child span per upstream attempt (so
    failovers show), with attributes for model, node, backend, status, ttft
    and tokens.
- **Backend spans:** vLLM's `--otlp-traces-endpoint` passes through `args:`
  in a serving file. The pinned image has the SDK. Documented with an
  example.

## Contract and version

**1.2.0.** Everything is additive (new endpoints, metrics, options, `ps`
columns, `status` values, JSON keys) except two behaviour fixes that touch the
error contract (decision 4):
- a configured model that is down answers 503 `model_unavailable` instead of
  404;
- a broken stream ends with an SSE error event instead of a cut.

`docs/compatibility.md` gets the metric names and labels, `/metrics/sd`, and
the `ps --json` keys.

## Decisions for Alex

1. Scope: all five as one release, **1.2.0**, published and deployed to
   ws, lab and orin like 1.1.x? (recommended)
2. Supervisor in the gateway (recommended), or systemd units per model?
3. Default restart policy for autostart models: `on-failure` (recommended;
   today a crash stays down) or opt-in only?
4. The error contract: a down configured model answers 503
   `model_unavailable` instead of 404, and broken streams end with an SSE
   error event. Accept both as fixes within 1.x (recommended), or keep 404
   until 2.0?
5. `/metrics` behind the API-key policy like `/v1/*`, or always open like
   `/healthz`? A0 suggests a separate scrape-only token, `llmctl config
   metrics-token`, so the monitoring host never holds a key that can run
   inference. It would cover `/metrics`, `/metrics/sd` and
   `/metrics/backends/*`; when it's unset, those fall back to the API key.
   vmagent sends a bearer token from a file, for scrapes and for HTTP SD.
   (recommended: the scrape-only token with that fallback)
6. No content-logging debug mode at all (recommended), or an explicit
   opt-in one?
